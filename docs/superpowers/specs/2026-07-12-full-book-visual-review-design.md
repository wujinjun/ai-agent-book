# 《AI Agent 从零到实战（2026版）》全书关系可视化复审设计

日期：2026-07-12  
状态：用户已批准方案 A，允许按推荐方案连续实施。

## 1. 目标与边界

本轮复审把“能用图更清楚表达的逻辑关系”从连续文字迁移为图、表或代码结构。目标不是增加装饰，而是降低读者理解流程、边界、状态、依赖、决策、数据和协作关系时的认知负担。

复审范围包括首页、七篇导读、第 1—38 章、十个项目、术语表、索引与出版产物。代码仍使用带语言标签的代码块；单一事实、定义和无需比较的短说明保留文字，不强制绘图。

## 2. 必须可视化的关系

出现以下任一结构时，默认必须提供图或表；只有视觉化会损失精度时才允许记录不适用理由：

1. 三个以上有顺序的步骤：流程图。
2. 两个以上参与者的往返交互：时序图。
3. 状态变化、终止、失败或恢复：状态图。
4. 三个以上组件的依赖或调用：架构图。
5. 数据经过多个阶段发生形态变化：数据流图。
6. 条件、路由、审批或选型分支：决策树。
7. 层级、所有权、信任边界或部署边界：分层架构图。
8. 多角色共享状态或协作：泳道图、时序图或 Blackboard 图。
9. 三个以上方案的多维比较：表格；只有两个连续维度时才使用象限图。
10. 概念之间的包含、依赖或区别：概念地图。

不使用无语义箭头、装饰性节点、虚假精度雷达图或把整段正文原样塞入节点的做法。

## 3. 覆盖目标

- 第 1—38 章：每章 3–5 张有效图，复杂章允许 6 张。
- 十个项目：每个项目 2–3 张，至少覆盖系统架构和运行/数据流。
- 七篇导读：每篇一张课程地图或能力依赖图。
- 首页：一张完整学习路径与能力地图。
- 预计最终总量 150–210 张，包含已有 76 张。

数量只是异常检测阈值，不是质量目标。表达同一关系的重复图必须合并；一张图承担两个互不相关主题时必须拆分。

## 4. 视觉语法

### 4.1 图形类型

- Mermaid `flowchart`：流程、数据流、架构和决策。
- Mermaid `sequenceDiagram`：Tool Calling、MCP、网络请求、审批与多 Agent 消息。
- Mermaid `stateDiagram-v2`：Agent Loop、任务、Checkpoint、Job 和恢复。
- Mermaid `graph`/`flowchart` 分区：层级、信任边界和部署拓扑。
- Markdown 表格：三维以上比较、能力矩阵和选型证据。
- 手写 SVG：Mermaid 无法清晰表达的概念地图、同心层、象限和课程地图。

概念插画只在抽象概念缺乏稳定结构表示时使用，且不得替代技术图。位图不承担精确架构信息。

### 4.2 方向与复杂度

- 普通流程默认从左到右，长生命周期从上到下。
- 时序图参与者不超过 6 个；超过时按边界拆图。
- 单图节点建议不超过 12 个，最大不超过 18 个。
- 每个决策分支写可执行条件，不写“视情况而定”。
- 状态图必须显示初始态、成功终态、失败态与可用恢复路径。
- 安全图必须显示外部输入、信任边界、高风险动作与审批点。

### 4.3 色彩语义

- 蓝色：正常控制流和核心组件。
- 灰色：数据、存储、背景服务和辅助信息。
- 橙色：人工审批、版本敏感项和降级。
- 红色：攻击、拒绝、越权和不可恢复错误。
- 绿色：验证成功、完成和安全终态。

Mermaid、SVG、PNG、HTML、PDF 和 EPUB 复用同一蓝灰视觉令牌、字体、线宽、圆角与留白。

## 5. 图文结合规则

每张图必须同时具备：

1. 图前引导段，说明图回答的问题。
2. 图题与稳定替代文本。
3. 图后解释段，说明阅读顺序、关键边界和工程结论。
4. 正文中对节点或关系的引用，而不是孤立插图。
5. 对版本敏感或存在争议的关系注明核对日期或观点边界。

图不能代替必要定义；文字也不能在图后逐节点机械复述。宽图在 HTML 中支持灯箱，PDF 中适配版心，EPUB 使用 SVG 首选与 PNG 回退。

## 6. 复审台账与自动审计

创建 `notes/visual-review.yml` 作为逐文件、逐节的可视化台账。每个关系单元记录：

- 源文件和小节标题；
- 关系类型；
- 处理方式：`diagram`、`table`、`code-structure` 或 `not-applicable`；
- 对应图形序号或不适用理由；
- 人工复审状态。

审计脚本输出以下失败：

- 章节或项目低于最低图形覆盖量；
- 台账中的关系单元没有处理结果；
- `not-applicable` 缺少具体理由；
- Mermaid 围栏无图前/图后解释；
- 图形缺失、空文件、alt 或图题；
- 单图节点过多、时序参与者过多或未显示错误/终止路径；
- HTML/PDF/EPUB 中仍出现 Mermaid 源码。

关键词检测只负责发现候选，不自动把段落改成图。最终关系分类和图形内容由人工复审确定。

## 7. 实施顺序

1. 建立台账格式、关系候选扫描器和覆盖测试。
2. 复审首页与七篇导读，建立全书视觉地图。
3. 按第一至第七篇顺序逐章补图和图后解释。
4. 为十个项目补系统架构、数据流/时序和部署/审批图。
5. 重新生成 Mermaid SVG/PNG 与图形清单。
6. 重建 HTML、PDF、EPUB，并运行资源与链接审计。
7. 生成全图缩略图联系表，逐张检查可读性、重复、裁切和语义色。
8. 抽检桌面、移动端、PDF 代表页和至少两个 EPUB 渲染路径。

每一篇作为独立可验证批次；后续批次不得覆盖前一批次已经通过复审的高质量图文。

## 8. 错误处理与可重复构建

图形源保持在 Markdown，渲染资产使用规范化源码哈希命名。源码不变时复用缓存；源码变化时生成新 ID。Mermaid 解析失败必须报告源文件、图序号和错误输出，不得退回源码展示。

构建过程不反向覆盖正文。生成文件先进入中间目录，审计通过后替换正式产物。图形、索引、术语和参考资料的生成步骤都进入 CI，生成结果漂移时构建失败。

## 9. 验收标准

1. 所有台账关系单元都有图、表、代码结构或明确不适用理由。
2. 38 章、10 项目、7 篇导读和首页达到覆盖阈值且无重复凑数图。
3. 每张图都有引导、图题、alt 和图后工程解释。
4. Mermaid 全部生成 SVG 与 PNG，清单稳定且资源审计为零问题。
5. HTML 三栏与移动布局无横向溢出，灯箱可用。
6. PDF 无裁切、重叠、过小文字和错误分页。
7. EPUB nav、SVG、PNG 回退和内部链接通过结构审计与两个渲染路径抽检。
8. Python 测试、Ruff、mypy、MkDocs strict build 与统一出版审计全部通过。
9. `PROJECT_STATUS.md` 准确记录已完成、人工抽检与任何仍需复验项。
