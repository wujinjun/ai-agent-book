# 常见学员错误与讲师处理

| 现象 | 常见原因 | 诊断顺序 | 讲师提示 |
|---|---|---|---|
| 把上下文当长期记忆 | 混淆输入窗口和持久存储 | 检查进程重启后的状态 | 让学员画出状态写入与读取路径 |
| Tool Calling 后函数没有执行 | 误以为模型执行本地代码 | 查看工具请求与执行日志 | 分离“模型提出调用”和“Runtime 执行” |
| JSON 偶尔解析失败 | 只用提示词约束格式 | 检查 Schema、校验和重试边界 | 要求增加非法输出 Fixture |
| RAG 有结果但答案错误 | 切分、过滤、重排或引用链路失效 | 从数据版本逐段检查 Recall | 禁止先调 Prompt 掩盖检索问题 |
| Agent 死循环 | 缺少步数、预算或状态终止条件 | 查看状态转换和重复工具调用 | 先实现确定性终止，再讨论 Reflection |
| Multi-Agent 成本失控 | 角色多但没有信息增益 | 与单 Agent 基线比较 | 删除不能改善成功率的角色 |
| 测试只能联网运行 | 依赖真实 Provider | 注入 Mock Transport 和稳定 Fixture | 将协议边界与模型质量测试分离 |
| 只保存最终答案 | 没有 Trace 和状态模型 | 检查工具、检索和审批证据 | 保存最小可审计事件而非全部敏感内容 |
| 重试造成重复写入 | 缺少幂等键和副作用分类 | 重放同一请求 | 写操作先设计幂等，再增加重试 |
| 把框架能力当模型能力 | 抽象层边界不清 | 标注模型、产品、框架、工程四层 | 用同一任务的原生实现对照 |

## 环境诊断顺序

```text
Python 版本 → 虚拟环境 → 固定依赖 → 配置文件 → Fixture → 单元测试
→ 服务健康检查 → 集成测试 → 在线 Provider
```

只有前一层通过后才进入下一层。这样可以避免把本地依赖冲突误判为模型问题，也避免一开始就消耗在线预算。
