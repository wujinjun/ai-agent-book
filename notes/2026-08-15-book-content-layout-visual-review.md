# 《AI Agent 从零到实战（2026版）》内容、排版与图文质量总审报告

审查日期：2026-08-15
审查性质：仓库维护范围内的全书编辑复审
审查对象：教材内容、章节结构、项目教学叙事、图示、HTML、PDF、EPUB
不在本轮范围：配套软件功能、示例程序实现、项目运行验证、自动测试、CI、外部账号与生产环境验证

## 1. 报告定位

本报告记录一次以读者体验和出版质量为中心的重新审查。它不因为文件存在、构建成功、图形能够渲染或章节达到最低字符数，就把内容判定为编辑完成。

此前的 `notes/final-content-review.md`、`notes/editorial-review.md` 和 `docs/QUALITY_ROADMAP.md` 主要证明仓库结构、最低内容门禁、图形资产和出版链路已经建立。本报告进一步检查这些内容在连续阅读、章节逻辑、移动阅读和纸质排版中的实际效果。若旧记录与本报告在“是否已经达到出版级内容和版式”上存在冲突，以本报告作为下一轮内容整改的当前基线。

## 2. 审查方法与证据范围

本轮完成了以下检查：

1. 盘点 38 个正文章节、7 个篇章首页、10 个项目 README、学习指南、术语表、参考资料和全书索引。
2. 检查全书标题层级、正文分布、章末结构、练习答案、引用方式和项目篇幅。
3. 复核 260 张 Mermaid/SVG 工程图的尺寸比例、信息密度和版面适应性。
4. 复核 48 张信息图的风格一致性、文字密度和图文分工。
5. 抽检 558 页 PDF 的封面、目录、前置材料、全部章首、正文页、代码、表格、章节结尾和后置材料。
6. 在桌面视口和 390 px 移动视口检查 HTML 首页及代表章节。
7. 检查 EPUB 的 XHTML 层级、样式表和媒体资源构成。

本报告不是逐字校对报告，也不替代出版社编辑、专业校对或法律意见；但它足以确定下一轮全书重编的优先级。

## 3. 总体结论

全书已经具备较强的工程内容基础，覆盖范围显著超过一般 API 教程，也能支持个人学习和企业课程使用。当前主要矛盾已经从“缺少内容”转变为“内容追加后没有完成全书级重组，图很多但缺少统一编辑，三种出版格式复用了同一套图稿和结构”。

当前成熟度估计如下：

| 使用目标 | 当前成熟度 | 主要限制 |
|---|---:|---|
| 个人系统学习 | 85%—90% | 部分章节顺序打断连续阅读，复杂图在小屏不易读 |
| 企业内部培训 | 80%—85% | 讲义材料较全，但正文与培训运营材料边界不清 |
| GitHub 开源展示 | 约 90% | 覆盖度和工程感强，仍有状态文本和视觉一致性问题 |
| 正式商业出版 | 60%—65% | 章节重编、图稿编辑、PDF 版式和 EPUB 轻量化尚未完成 |
| 十个生产项目模板 | 55%—65% | 代码仓库说明存在，但项目教学章节不够完整 |

结论：下一阶段不应继续按数量增加章节或插图，而应进入重组、删减、合并、重绘和分格式排版阶段。

## 4. P0：阻碍正式出版的问题

### P0-1 章节逻辑层级断裂

27 个章节在“总结、练习、面试与阅读”之后仍有多个核心三级标题。读者、HTML 右侧目录和 EPUB 导航都会把这些内容理解为总结的子内容。

受影响章节：

- 第 6—10 章；
- 第 14—35 章均存在不同程度问题；
- 共计 27 章。

严重案例：

| 章节 | 总结标题位置 | 总结标题之后的正文比例 | 问题表现 |
|---|---:|---:|---|
| 第23章 Python Agent 工程基础 | 第31行 | 约91% | 几乎全部核心内容都位于总结之后 |
| 第16章 向量数据库 | 第51行 | 约82% | 数据库原理、索引与选型成为总结子节 |
| 第28章 Observability | 第60行 | 约79% | 日志、指标、Trace 等主体内容位于总结之后 |
| 第32章 Multi-Agent 原理 | 第60行 | 约76% | 主要协作模式和终止机制位于总结之后 |
| 第21章 LangChain 与 LlamaIndex | 第69行 | 约75% | 当前框架边界和核心抽象位于总结之后 |
| 第18章 OpenAI Agents SDK | 第76行 | 约70% | Agent、Tool、Runner、Handoff 等主体内容位于总结之后 |

问题来源是早期短版章节与后期扩写内容直接追加，没有进行章节级重编。整改时不能只移动一个标题；需要合并前部摘要与后部详述、去除重复段落，并按概念依赖重新组织二级标题。

### P0-2 工程图比例不适合纸张和小屏

现有 260 张工程图中：

- 103 张宽高比超过 4:1；
- 69 张宽高比超过 6:1；
- 22 张宽高比超过 10:1；
- 另有少数过度纵长的图。

代表性极端图：

| 图示 ID | 约宽高比 | 主要风险 |
|---|---:|---|
| `agent-product-readiness-gates` | 29.3:1 | A4 中被压成细线，标签无法阅读 |
| `framework-selection-evidence-funnel` | 28.9:1 | 结构过宽，选择逻辑无法快速扫描 |
| `fastapi-request-security-lifecycle` | 23.9:1 | 生命周期与安全边界挤在一条横链 |
| `deployment-schema-expand-contract` | 20.9:1 | 阶段过多，电子书缩放后不可读 |
| `multimodal-rag-main-pipeline` | 19.3:1 | 主流程应拆为总览和局部阶段 |

图能够渲染不等于图能够阅读。所有超过 6:1 的图都应进入重新设计队列，优先采用纵向流程、分泳道、分阶段或“总览图＋局部图”。

### P0-3 信息图信息过载且风格不统一

当前信息图混合了平面矢量、3D 等距图标、仪表盘、角色插画和海报式网格。部分图承担了过多任务，把架构、流程、风险、评估与部署同时塞进一张图。

重点复审对象：

- `generation-control-infographic`；
- `vector-index-migration-infographic`；
- `multimodal-evidence-infographic`；
- `project08-research-workflow-infographic`；
- `agent-security-trust-boundary-infographic`；
- `project09-multi-agent-dev-infographic`；
- `framework-selection-map-infographic`；
- `agent-data-storage-infographic`；
- `tool-permission-execution-infographic`。

移动端实测中，第23章纵向信息图缩至约 341 px 宽后，图中文字已经无法承担教学信息。信息图应遵循“一张图回答一个问题”，复杂主题拆成一张总览和两至三张局部图。

### P0-4 PDF 仍是课程资料排版，不是正式图书排版

当前 PDF 共 558 页，主要问题如下：

1. 封面标题出现不自然断行，封面带页码。
2. 目录多页、双栏、字号偏小，篇章层级不够醒目。
3. 第一章约到第 40 页才开始，前置材料过长。
4. 企业培训、学员验收、互评模板和内部状态材料占用正文前后空间。
5. 多个章节尾页只有一小段内容，留白过多。
6. 宽图被压缩成细带，简单纵向图又可能独占一页。
7. 代码字体和高亮颜色偏浅，纸质阅读费力。
8. 部分表格字体偏小。
9. 章首信息图位置不一致，缺少稳定的视觉节奏。
10. 书末状态清单带有内部项目管理感，不适合作为正式图书后记结构。

讲师手册、学员材料、验收模板和维护者状态应迁移到附录或独立培训手册，正文只保留读者需要的内容。

### P0-5 EPUB 体积和图稿没有针对电子阅读优化

当前 EPUB 大小约 128.5 MiB，资源构成为：

| 类型 | 数量 | 未压缩体积 |
|---|---:|---:|
| PNG | 309 | 约 127.75 MiB |
| SVG | 259 | 约 5.51 MiB |
| XHTML | 77 | 约 1.48 MiB |

部分单张 PNG 达到 3—4 MiB。高分辨率图片没有解决小屏文字过密，反而增加打开、翻页和分发成本。EPUB 需要独立图片版本：降低位图分辨率、拆分纵向海报、保留适量 SVG，并避免无必要地同时收录重复格式。

### P0-6 十个项目缺少真正的项目教材叙事

项目 README 篇幅约为 3,117—5,956 个字符，能够说明如何运行代码，但不足以承担完整实战章节。

| 项目 | README 字符数（约） |
|---|---:|
| 项目1 最小 AI Assistant | 3,166 |
| 项目2 天气与工具调用 Agent | 3,117 |
| 项目3 MCP 本地工具 Agent | 3,570 |
| 项目4 企业知识库 Agent | 4,605 |
| 项目5 代码 Review Agent | 4,274 |
| 项目6 自动办公 Agent | 4,578 |
| 项目7 股票研究 Agent | 3,191 |
| 项目8 LangGraph 研究工作流 | 5,721 |
| 项目9 Multi-Agent 开发团队 | 4,659 |
| 项目10 企业级 Agent 平台 | 5,956 |

每个项目需要增加独立教学章节，至少包含需求推导、用户流程、架构选择、逐步实现、关键代码解释、样例输出、失败排查、安全边界、观测、部署、复盘和扩展练习。README 保留安装与运行职责，不与教材章节混用。

## 5. P1：重要内容编辑问题

### P1-1 章节模板机械化

大量章节使用相同的五段式标题。模板保证了最低覆盖，却没有体现不同主题的自然逻辑。正文标题应服从主题：Transformer 应围绕结构与 Attention；Tool Calling 应围绕协议、循环、失败和授权；Docker 应围绕镜像、配置、网络、状态与回滚。

### P1-2 缺少贯穿全书的主案例

示例在知识库 Agent、研究 Agent、工具 Agent 和企业平台之间频繁切换。建议选择“企业知识助手”作为主线，从 Prompt、结构化输出、Tool Calling、Runtime、MCP、RAG、Memory、LangGraph、FastAPI、Evaluation、安全和部署逐章扩展。其余场景作为对比案例。

### P1-3 框架版本证据压过教学叙事

第17—22章对版本、验证和官方接口边界记录较多，这些内容应压缩为统一的版本侧栏。正文应使用同一个任务横向比较原生 API、OpenAI Agents SDK、PydanticAI、LangGraph、LangChain/LlamaIndex 和多 Agent 框架分别管理了哪些复杂性。

### P1-4 引用未与具体论断就近绑定

全书有丰富的章末参考资料，但正文中指向统一参考文献锚点的就近引用为 0。重要数字、版本、论文方法、安全分类、评估指标和争议观点需要在相邻段落中明确标注来源。章末书目可以保留，但不能承担全部证据关系。

### P1-5 练习答案过早暴露

38章中有37章直接包含练习参考答案。建议正文只保留题目，答案移至书末或教师版；题目按概念、设计、编码和故障实验分类，并增加可验证的完成标准。

### P1-6 学习指南的 24 周路线没有逐周展开

8周和12周路线较清楚，但24周路线把第13—23周合并为阶段，没有逐周列出章节、时间、编码任务、成果与检查标准，不满足最初课程设计要求。

### P1-7 术语表和索引不足以覆盖 558 页教材

术语表只有三十多个主要词条，应补充生成参数、检索指标、向量索引、分布式任务、可观测性、安全和工作流术语。当前全书索引是术语出现次数统计，更接近 Concordance，不是真正定位到小节或页码的出版索引。

### P1-8 各篇首页状态与全书状态矛盾

部分篇章首页仍使用“初稿完成”“需核查”“官方 SDK 待实测”等旧状态，与当前项目状态记录不一致。正式读者版应删除开发进度语言，维护状态只保留在仓库内部文档。

### P1-9 中英文术语与大小写不统一

Handoff/handoff/移交、Guardrail/guardrail/护栏、Tool/tool/工具、Memory/memory/记忆等写法需要统一。应制定首现写法、后续写法、产品名、API 标识符和一般概念的明确规则。

### P1-10 网站导航暴露过多维护者页面

HTML 主导航包含质量路线图、最终验收状态和项目状态。它们适合仓库维护者，不适合普通读者的主导航。读者导航应以阅读路径、篇章、项目、术语和参考资料为主。

## 6. P2：出版润色问题

1. 重新设计封面与七篇分隔页。
2. 统一页眉、页脚、篇名、章名和页码策略。
3. 统一图题、表题、代码清单编号及正文交叉引用。
4. 避免图题与图片跨页，减少不足半页的章末页。
5. 代码采用更高对比度的印刷配色；长代码仅展示关键片段。
6. 检查黑白打印，不能只靠颜色表达语义。
7. 统一信息图色板、字体、图标、线宽、圆角和阴影规则。
8. 项目篇应按项目1至项目10递进，不在项目1之前展示项目10的完整架构图。
9. 对所有含文字图稿建立最小字号门禁：PDF 100% 缩放、390 px 网页和主流 EPUB 阅读宽度下均可读。
10. 书末应以总结、附录、术语、参考文献和索引收束，不以内部状态清单收束。

## 8. 编辑原则

后续整改应遵循以下原则：

- 不以字数、图数和文件存在性代替编辑判断。
- 一张图只承担一个主要问题；复杂系统采用总览和局部分层表达。
- 图与正文必须分工：图表达关系，正文解释原因、边界和例外。
- Mermaid 保留精确、可维护的工程关系；出版信息图承担概念全景和视觉导读。
- 不为追求“图文结合”把定义、代码语义或争议观点强行图片化。
- 每章必须有清晰进入路径、概念递进、工程案例、失败路径和真正的章末收束。
- HTML、PDF 和 EPUB 使用同一内容源，但允许采用不同图片尺寸、分页和导航策略。
- 软件和测试的既有状态不在本轮整改范围内，除非正文中的说明与事实明显矛盾。

## 9. 最终判断

这本书已经拥有足够的技术覆盖和素材储备。下一轮质量提升的关键不是继续堆叠，而是像正式出版社编辑一样进行结构重编、视觉取舍和分格式排版。完成全部 P0 项后，商业出版成熟度可接近 80%；完成 P1 和 P2 后，才适合进入终校、试读和正式发行阶段。
